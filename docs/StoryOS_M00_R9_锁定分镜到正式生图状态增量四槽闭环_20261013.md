# StoryOS M00 R9：锁定分镜 → 正式生图状态增量四槽接入（2026-10-13）

## 背景与约束

R8 原生 Codex 实图 C02-T01 相对 C02-R2 的脚步、车轮位置和街景结构有改善，但手/把接触和低端安卓设备时代感仍需复核，记录状态为 `UNCERTAIN_NEEDS_FULL_REVIEW`，不得以这轮代码合并将旧图宣布为 PASS。

R9 将 R8 的**可观察状态变化**接入生产链，同时坚持 **只有锁定分镜能授权新剧情**。本轮只更改代码和离线测试，不修改任何正式 Episode、MySQL、用户上传参考图或先前图片；没有凭空创建正式 Episode Review Authority。

## 四槽

**① 来源锁定与 SHA。** 如果且仅当 Episode 的正式 Release Manifest 所引用的 **JSON Storyboard** 的相邻帧对象中含有 `m00_adjacent_state_delta` 字段，且当前视觉风格是 M00、帧序号 > 1，`frame_contract.compile_frame` 才使用现有 `m00_sequence_state_delta.canonical` 验证并派生固定人物、衣物、道具、环境、摄影者、光线的合约及前后可见变化。原始当前帧和上一帧的 storyboard excerpt SHA 与状态增量 SHA 一起绑定进**此帧** Frame Contract SHA。没有字段的老帧**不新增 hash material 键，不改旧 Frame Contract SHA**，M01 及其他风格不附加 M00 限制。Markdown 分镜当前没有该字段的结构化入口，不自动从自然语言推测新事件。

示例（位于正式 JSON 分镜中已有的第二帧对象，不是独立的第二套创作权威）：

```json
{
  "frame": 2,
  "scene": "与第一帧同一位成年人向前推动原来的自行车",
  "m00_adjacent_state_delta": {
    "schema_version": 1,
    "mode": "action",
    "locked": {
      "identity": "与上一帧同一位成年人，外貌和身形不变",
      "wardrobe": "沿用上一帧深色夹克和旧鞋，不换衣服",
      "props": "同一辆旧自行车，车架、轮圈和车座不变",
      "geography": "同一条旧街巷，墙体和门窗结构不变",
      "photographer": "同一摄影者在路边后方，机位物理可达",
      "lighting": "同一个阴天，使用自然散射光"
    },
    "observable_changes": [
      {
        "id": "shoe_step",
        "before": "上一帧近侧鞋子仍踩在上一位置的湿地",
        "after": "这一帧近侧鞋已向前迈步并踩在新位置",
        "pixel_evidence": "两帧近侧鞋的位置不同且仍有真实着地关系"
      },
      {
        "id": "front_wheel",
        "before": "上一帧自行车前轮还在水洼前一条砖缝旁",
        "after": "这一帧自行车前轮已经滚过新的砖缝位置",
        "pixel_evidence": "前轮与固定墙缝距离改变且车架实体连续"
      }
    ]
  }
}
```

静止分镜使用 `mode=static` + `observable_changes=[]`，不会强制制造动作。

**② 真实 Provider Payload。** `Frame Contract → Prompt Package → Image Worker → Image Controller → canonical image.payload` 逐层携带 Delta JSON 和 Delta SHA，成功的文本 Controller 不能偷偷删掉状态变化，也不能夹带未授权状态。最终带入原生 Codex 图片模型的 `scene_prompt`，并参与真实 Payload Request fingerprint。若来源合同内容或 SHA 漂移则在付费 Provider 前 fail-closed；不启用的老帧继续原 Controller 输入指纹构造方法，避免仅因 None 字段导致历史请求变化。原生 Codex 经原有 Gateway/MySQL Attempt/全局 5 个容量名额派发，绝无 OpenCodex 代理或第二种图像网关。

**③ 真实像素复核。** `m00_episode_delta_review.inspect_pair` 与 `scripts/storyos_m00_episode_delta_audit_r9.py` 对已存在的相邻原图做纯只读 SHA、Pillow 像素存在性和两图逐项审核：身份、服装、道具、建筑、摄影者、光照以及每个授权变化，图片都必须位于该 Episode 工作区。缺图、来源 SHA 漂移、未写齐审核字段一律不能 PASS；动作帧前后像素完全相同直接标 `DUPLICATE_ACTION_PIXELS`，静止帧不强制变化。即使完成审核，只返回 `ADVISORY_PIXEL_PASS`，**绝不构成正式 Final Semantic Review、Visual Lock、MySQL Attempt 或发布权威**。正式 Critic 提示词新增专门针对显式 M00 Delta 的双帧像素检查要求，仍由原 canonical 审核流程执行。

**④ 测试、隔离与清理。** 全部代码在独立 Worktree 中开发，各槽使用快速 pytest，统一入口加入 R9 回归，最终全槽 `--slot all` 与 `--slot all --stress`；主线并发移动时先 rebase/复测，只有无冲突且用户脏文件不与目标重叠才 fast-forward 推送。Worktree 退役必须使用 `storyos_retired_worktree_gc.py` 的 plan 后检查 72h、无脏文件/活跃进程、主线及远端合并祖先，禁止强制删除新工作树。

## 运维，只读（不会调用 Codex Provider）

```powershell
python scripts/storyos_m00_episode_delta_audit_r9.py EPISODE_DIRECTORY --frame 2
python scripts/storyos_m00_episode_delta_audit_r9.py EPISODE_DIRECTORY --frame 2 --previous-image media/approved/01.png --current-image media/approved/02.png
```

输出的 `SOURCE_LOCKED_AWAITING_PIXELS`、`PENDING_FULL_PIXEL_REVIEW` 或 `UNCERTAIN_NEEDS_FULL_REVIEW` 都是事实状态，不是自动验收许可。任何正式 Episode 生图仍必须完整通过已有 PREIMAGE、Visual Lock、预算与 Production Authority，而不能用此咨询性工具代替。
