# StoryOS M00 R7：连续分镜原生图片校准（2026-10-13）

## 与 R6 的区别

R6 已证明 C02-R2 的推车动作有进步、C04-R2 的悬浮异常事件真实可见，但两张照片各自独立，不能证明**同一个人、同一辆车、同一摄影者跨帧不会漂移**。

R7 不改生产母画风，不添加全局“必须走路/骑车/异常”等创作限制，而是创建独立、两帧连续的 Test-only 示例，沿用 R6 用户已登录的原生 Codex Bridge 和共享容量；所有旧照片保持只读。

## 四槽验收

1. **人物与道具连续性。** 锁定 C02-R2 原始实图与 SHA，下一张 S01 的前驱是 C02-R2，S02 的前驱只能是 S01。最多两张参考图：前驱图片 `identity`，一个用户私有参考 `capture_style`。两种权限有界，不将用户原始样图人物/地点/故事复制到内容中。人的深灰夹克、鞋子、自行车后货架/挡泥板、右侧旧墙等都在本 Test-only 案例明确列出。
2. **物理机位和事件增量。** 摄影者位于人物后左侧且相邻帧保持可到达位置，故事每帧向前推进约 1–2 秒，不能假装固定照片裁切就是故事进展，不强制运动模糊、不伪造导演机位。相邻帧仍由指定 CP02 的物理合同拍摄，而不是默认 CP01。
3. **相邻实际像素验收。** `pair-review` 只有同时核对前后真实 PNG 和对应 SHA/Provider 回执，且有审核人、两张完整原图观察说明与七项 PASS/FAIL/UNCERTAIN，才可能给出 **ADVISORY_PAIR_PASS**；任意 FAIL 触发 REPAIR_RECOMMENDED。不能伪造成正式 Visual Lock/Release/Attempt 权威。
4. **原生执行/极速与治理。** 复用 `storyos_m00_calibration_r2.execute_bundle`：公共图片容量锁、单请求指纹、独占创建 Test-only 回执、原生 Codex 用户态 Bridge；超时/UNKNOWN 不自动重试。Worktree 清理遵守 AGENTS.md 的 72 小时及未提交/合并祖先检查。

python -m pytest -q tests/system/test_m00_sequence_r7.py

先准备（不付费、不生图）：

```powershell
python scripts/storyos_m00_sequence_r7.py plan --frame S01
```

**真实 Test-only 生图（须显式确认）**：

```powershell
python scripts/storyos_m00_sequence_r7.py run --frame S01 --ack-testonly-paid-image
```

**R7 实图反馈后新增防扩散门禁：** S01 的原生回执/PNG/SHA 成功，仅证明文件存在，不授权自动执行 S02。必须先执行 `pair-review --frame S01`，真实检查两张完整原图，将包含七项判断的 `C02-S01/pair-review.json` 留在私有目录，且其 SHA 绑定的审核结果为 `ADVISORY_PAIR_PASS`，才允许 `plan --frame S02` / `run --frame S02 --ack-testonly-paid-image`。前驱审核文件本身的 SHA 也进入 S02 请求指纹；审核发生漂移时拒绝继续派发。若出现 FAIL / UNCERTAIN / 审核缺失，即使 PNG 文件和用户登录全部有效，也必须停止在原地返修，不能用模型覆盖已有图片或悄悄继续扩散错误。**这只是 Test-only 实验的质量准入，不是正式 Episode Visual Lock Authority。**

测试私有路径：`.storyos/user-visual-references/test-only-calibration/C02-S01/` 和 `C02-S02/`，图像不进入 Git。正式项目需要自主绑定合法 Episode Stage/MySQL/Review 后才允许生产，Test-only 绝不授予这种权限。
