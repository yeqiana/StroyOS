# StoryOS R6 四槽极速工程验收（2026-10-13）

## 本轮已实现的四槽

**槽位 1 · 已退役 Worktree／分支治理。** `scripts/storyos_retired_worktree_gc.py` 继续默认只读，对 Worktree 严格要求 Git 已登记、位于官方直接子目录、工作区及未跟踪文件干净、超过 72 小时且无进程引用、同时为本地/远端主分支祖先。新增拒绝 `inf`、`nan` 和布尔年龄的检查；本地分支删除前以 `git rev-parse --verify` 对同一引用执行两次 SHA 检查，若中间被其他 Codex 任务更新则拒绝，随后仍只使用 `git branch -d`。本轮实际安全删除本地已合并分支 `feature/storyos-native-codex-full-auto-entry-20261010`；本轮盘点的 71 个登记 Worktree 中无符合全部退役条件的对象，因此没有强制删除。

**槽位 2 · 真实 Provider 模糊结果门禁。** `image_generation_gateway.py` 在 canonical Generation Attempt/MySQL Fence、全局五图 Permit 之后调用官方 Provider。如果**确已进入 Provider 调用**，而出现 Python `TimeoutError`、`ConnectionError`、原生 Codex 进程 `subprocess.TimeoutExpired`，结果不能安全判断是否收费：尝试持久化 `OUTCOME_UNKNOWN`，保留已经消耗的 Attempt，不能自动当成失败重试。只有显式可证明的其他 Provider 异常才沿用 `FAILED_AFTER_DISPATCH` 既有路径。对批量任务，已经成功持久化 `mark_observed` 的帧不可因为后续帧回执失败再被标成 UNKNOWN；仅保守处理尚未记录的剩余帧。若终态数据库再次不可用，保持已消费和未验证，不构造假的成功回执。

**槽位 3 · 原生 Codex 登录上下文进入 Frame01 前后双检。** `storyos_autonomy_canary.py plan` 现在联合 `storyos_autonomy_native_ready.report`，只使用真实 Codex CLI 的 `--version`、`exec --help` 和 StoryOS 交互 Runner 登录健康检查。第一次和最后一次证据不同、没有登录上下文、疑似代理或不可信进程调用均 `BLOCKED`；仍要求 MySQL Stage、Attempt、Frame01 不变。可见登录态 ≠ 图片模型账号权限 ≠ 真实付费生图成功；即使均绿也只返回 `EVIDENCE_ONLY`、`can_dispatch_image=false`。不使用 OpenCodex、不会启动 `codex exec` 或消耗模型次数。

**槽位 4 · 四槽故障注入及最终极限验证。** 覆盖时间字段污染、Git 分支提交变化、Provider 单帧/批量网络超时、批量前帧已确认回执、CLI 认证前后漂移、无权限以及跨路径拒绝。R1-R5 历史 Runtime、Writer、Episode、共享五图容量测试维持原有全量回归。各槽 TDD 在修改前先得到预期 RED、修复后立即 GREEN。
