# StoryOS M00 R6 — 四槽位实图校准闭环（2026-10-13）

## 动机

旧 C02/C04 实图确为原生 Codex 生成，但旧本地实验脚本对所有场景都使用默认 CP01，没有透传计划中的 CP02/CP03。C02 的人物和自行车接触/位移证据偏弱，C04 的“由故事定义的异常”未具体定义，导致出图变成普通生活场景。上一轮 R5 已修生产视觉合同，本轮聚焦独立真实测试的接入及评价。

## 四槽

1. **设备合同**：`scripts/storyos_m00_calibration_r2.py` 从用户私有计划取每帧设备选择，对照 CP02/CP03 注册表和设备源 SHA，将旧 Test-only visual contract 设备节精准替换，调用 M00 风格、可见事件、动作守卫生成唯一有指纹的原生 Codex 请求。
2. **C02 动作**：新增独立版本 `C02-R2`，明确抓车把/车座、前步重心、轮胎接触浅水与离墙距离等真实动作证据，禁止为了“动态”机械增加运动模糊。
3. **C04 异常**：新增独立版本 `C04-R2`，将抽象的“未知异常”定义成石子在地砖上空约 8cm 悬浮，必须有清晰空气缝隙、正确实体阴影、尺度及住户视线。这个具体事件**仅属于 Test-only 本例**，绝不进入 M00 母风格或已有 Episode。
4. **Provider/像素回执**：原图 SHA、计划 SHA、设备 SHA、最终场景 Prompt SHA、参考图类型进入实验指纹；同图一次真实 `image_generation`；使用同仓库共享图片容量守卫。开始派发前独占创建回执，任何中断不自动重试；超时可按**原 request_id + 原 thread_id**只读找回已生成工件，仍标记 `IMAGE_RECOVERED_AFTER_RUNNER_TIMEOUT`，不假装正常完成或正式权威。比较旧图/新图时只是 `PENDING_ACTUAL_PIXELS`，必须另做肉眼/视觉审核。

## 本地操作（不使用 OpenCodex）

先检查（不生图）：

```powershell
python scripts/storyos_m00_calibration_r2.py plan --case C02
python scripts/storyos_m00_calibration_r2.py plan --case C04
```

真实实验（会调用原生 Codex，使用用户已登录的 Bridge，必须显式授权且不需要正式 Episode/MySQL Attempt）：

```powershell
python scripts/storyos_m00_calibration_r2.py run --case C02 --ack-testonly-paid-image
python scripts/storyos_m00_calibration_r2.py run --case C04 --ack-testonly-paid-image
```

之后 `status --case C02` 和 `status --case C04`，如遇 UNKNOWN **先核实持久化原请求证据**，可使用 `recover --case C02` / `recover --case C04`，但不能再次 run。原版 `C02`/ `C04` 不覆盖，新图在 `.storyos/user-visual-references/test-only-calibration/C02-R2/`、`C04-R2/`；全目录被 .gitignore 排除，不能上传 Git。

本轮不触碰正式 Episode / MySQL；生产 Gate/Visual Lock/发布权威不会接受这些测试 mock。图像分辨率（如 1122×1402）不能当作已完成 1080×1350 的正式生产像素归一化。
